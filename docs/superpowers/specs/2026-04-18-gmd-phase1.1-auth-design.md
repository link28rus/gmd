# GMD Phase 1.1 — Auth + Family

**Дата:** 2026-04-18
**Фаза:** 1.1 (часть Phase 1 «Backend core»)
**Зависит от:** Phase 0.3 (prod-стек, Prisma, Redis, SMTP-ready)

## Цель

Родитель может зарегистрироваться и войти в систему по email с OTP-подтверждением, получив привязанный контекст «семьи» для всех последующих фич (locations, geofences, SOS).

## Scope

**Входит:**

- Passwordless email-OTP flow (`request-otp` + `verify-otp`).
- JWT access-token (RS256, 15m) + opaque refresh-token с ротацией и replay-detection (30d).
- Модели `User`, `Family`, `Membership`, `OtpCode`, `RefreshToken`.
- `GET /me`, `PATCH /me`, `PATCH /family/:id`, `POST /auth/logout`, `DELETE /me` (soft-delete).
- Rate limiting через `@nestjs/throttler` + Redis.
- Dev-окружение: MailHog. Prod-окружение: произвольный SMTP.
- TDD: unit + integration + OpenAPI contract.

**Не входит** (Phase 1.2 и далее):

- Child invite / QR-поток / device-token для детских устройств.
- Onboarding UI (имя родителя и семьи собираются post-factum через `PATCH /me` и `PATCH /family`).
- 2FA, WebAuthn, passkeys.
- Password-based login (passwordless by design).
- Экран «Активные сессии» в кабинете (данные уже копятся в БД, UI потом).
- Email-verification reminder, welcome-email — только код регистрации в 1.1.

## Решения (зафиксированы через brainstorming)

| Вопрос               | Решение                                                                                                  | Почему                                                                                           |
| -------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Метод аутентификации | Email + OTP (6 цифр)                                                                                     | Бесплатно в dev (MailHog) и prod (Brevo free-tier / SMTP), универсально, заменяет password-reset |
| Регистрация vs логин | Passwordless one-step (`request-otp` → `verify-otp`; первая verify = auto-register + auto-create Family) | Минус экран в UI, стандартный UX magic-link                                                      |
| Refresh-token        | Opaque в БД, rotation on use, replay detection                                                           | Нужна возможность «разлогинить все устройства», видимость активных сессий                        |
| Access-token         | JWT RS256, 15m, claims `{sub, familyId, role}`                                                           | Подпись асимметрична → можно валидировать offline на фронте, если понадобится                    |
| Scope Phase 1.1      | Auth + Family + Membership                                                                               | Без family-контекста все дальнейшие фичи потребуют retrofit                                      |

## Архитектура

### Data model (Prisma)

```prisma
model User {
  id                            String    @id @default(cuid())
  email                         String    @unique
  emailVerifiedAt               DateTime?
  name                          String?
  locale                        String    @default("ru")
  acceptedPrivacyPolicyVersion  String?
  createdAt                     DateTime  @default(now())
  updatedAt                     DateTime  @updatedAt
  deletedAt                     DateTime?

  memberships   Membership[]
  refreshTokens RefreshToken[]
  otpCodes      OtpCode[]

  @@index([email])
  @@map("users")
}

model Family {
  id        String    @id @default(cuid())
  name      String    @default("Моя семья")
  createdAt DateTime  @default(now())
  updatedAt DateTime  @updatedAt
  deletedAt DateTime?

  memberships Membership[]

  @@map("families")
}

enum MembershipRole {
  owner
  parent
}

model Membership {
  id        String          @id @default(cuid())
  userId    String
  familyId  String
  role      MembershipRole
  createdAt DateTime        @default(now())

  user   User   @relation(fields: [userId], references: [id], onDelete: Cascade)
  family Family @relation(fields: [familyId], references: [id], onDelete: Cascade)

  @@unique([userId, familyId])
  @@index([familyId])
  @@map("memberships")
}

model OtpCode {
  id         String    @id @default(cuid())
  userId     String?
  email      String
  codeHash   String
  purpose    String    @default("login")
  expiresAt  DateTime
  consumedAt DateTime?
  attempts   Int       @default(0)
  createdAt  DateTime  @default(now())

  user User? @relation(fields: [userId], references: [id], onDelete: SetNull)

  @@index([email, createdAt])
  @@map("otp_codes")
}

model RefreshToken {
  id          String    @id @default(cuid())
  userId      String
  tokenHash   String    @unique
  userAgent   String?
  ipAddress   String?
  expiresAt   DateTime
  revokedAt   DateTime?
  rotatedToId String?
  createdAt   DateTime  @default(now())

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId, revokedAt])
  @@map("refresh_tokens")
}
```

**Soft-delete:** `User.deletedAt` и `Family.deletedAt`. Hard-delete через 30 дней — отдельный cron-job в Phase 1.3 (вне scope 1.1, в коде закладываем `deletedAt` фильтр во всех запросах).

### API (REST, OpenAPI 3.1)

```
POST /auth/request-otp
  body:     { email }
  202:      { expiresIn: 600 }
  429:      { error: { code: "rate_limited" } }

POST /auth/verify-otp
  body:     { email, code }
  200:      { accessToken, refreshToken,
              user: { id, email, name },
              family: { id, name } }
  400:      { error: { code: "invalid_code" | "code_expired" | "code_consumed" } }
  429:      { error: { code: "rate_limited" } }

POST /auth/refresh
  body:     { refreshToken }
  200:      { accessToken, refreshToken }      // rotation: старый revoke
  401:      { error: { code: "refresh_invalid" } }
              + если detected replay — revoke всей цепочки refresh-токенов пользователя

POST /auth/logout
  body:     { refreshToken }
  204:      (revoke текущего token; access живёт ≤15m, клиент его выбрасывает)

GET  /me                                 (Auth: JwtAuthGuard)
  200:      { user, family, memberships: [{ role, familyId }] }

PATCH /me                                (Auth)
  body:     { name?, locale? }
  200:      { user }

PATCH /family/:id                        (Auth: role=owner в этой семье)
  body:     { name? }
  200:      { family }
  403:      { error: { code: "forbidden" } }

DELETE /me                               (Auth)
  204:      (soft-delete User; все refresh-токены revoked; family soft-delete если последний owner)
```

**Unified error format:** `{ error: { code: string, message: string, details?: unknown } }` через global `HttpExceptionFilter`.

**OpenAPI-first:** схема `packages/shared-types/openapi/auth.yaml`. Codegen → TS (web) и Dart (mobile). Lint: openapi соответствует реальным ответам (jest matcher из `@apidevtools/swagger-parser`).

## Безопасность

### OTP

- 6 цифр, `crypto.randomInt(100000, 1000000)`.
- TTL 10 минут.
- В БД — `argon2id(code + per-code-salt)`, никогда plain.
- Одноразовый: `consumedAt` выставляется при успешной verify.
- 3 неудачных попытки → код invalidate (`consumedAt = now()` с меткой неуспеха).
- Новый `request-otp` на тот же email **invalidate** предыдущий активный код на этот email.

### Refresh-token

- 32-byte random → base64url → клиенту.
- В БД — `sha256(token)` в `tokenHash @unique`.
- Rotation on use (`/auth/refresh` всегда выдаёт новый, старый revoke, цепочка через `rotatedToId`).
- **Replay detection:** клиент прислал refresh с `revokedAt != NULL` и `rotatedToId != NULL` → это украденный токен. Сервер revoke'ит **всю цепочку refresh-токенов этого `userId`**, клиент получает 401 и вынужден залогиниться заново.

### Access-token (JWT)

- Алгоритм RS256. Ключи: `JWT_PRIVATE_KEY` / `JWT_PUBLIC_KEY` в PEM, генерируются одноразово через `pnpm --filter @gmd/backend auth:keygen`.
- Claims: `{ sub: userId, familyId: string, role: MembershipRole, iat, exp }`.
- Clock-skew tolerance: 30s.

### Rate limiting (`@nestjs/throttler` + Redis)

| Endpoint                             | Лимит                                         |
| ------------------------------------ | --------------------------------------------- |
| `POST /auth/request-otp`             | 3 req / 10 min / email + 20 req / 10 min / IP |
| `POST /auth/verify-otp`              | 10 req / 10 min / IP                          |
| `POST /auth/refresh`                 | 30 req / min / IP                             |
| `POST /auth/logout`                  | 30 req / min / IP                             |
| `GET/PATCH /me`, `PATCH /family/:id` | 60 req / min / IP                             |
| `DELETE /me`                         | 5 req / 10 min / user                         |

Per-user лимит реализуется кастомным `ThrottlerStorage` с ключом `userId` для authenticated endpoints.

### Защита от enumeration

- `POST /auth/request-otp` всегда отвечает `202`, даже если email не существует.
- Минимальная задержка ответа 200ms (`setTimeout` до `min`) — защита от timing attack по наличию user.

### Защита от брутфорса emails

- > 10 неудачных `verify-otp` с одного IP за 10 минут на разные email'ы → IP в temporary ban (Redis key `ban:ip:<ip>` TTL 1h) + ответ 429 на любой `/auth/*` endpoint.

### Cookies vs Header (клиенты)

| Клиент           | access-token                           | refresh-token                                               |
| ---------------- | -------------------------------------- | ----------------------------------------------------------- |
| Mobile (Flutter) | `Authorization: Bearer …`              | в теле `/auth/refresh`, хранится в `flutter_secure_storage` |
| Web (Next.js)    | в памяти (Zustand / React Query cache) | `httpOnly + Secure + SameSite=Strict` cookie `gmd_refresh`  |

Web не видит refresh из JS → защита от XSS кражи. Mobile secure-storage — iOS Keychain / Android Keystore.

### Логирование и PII

- Структурированные логи (pino): `auth.request_otp`, `auth.verify_ok`, `auth.verify_fail`, `auth.refresh_rotated`, `auth.refresh_replay_detected`, `auth.logout`, `auth.account_deleted`.
- Email в логах — не plain; используется `emailHash = sha256(email).slice(0,8)` для корреляции.
- Полный email — только в `OtpCode.email` в БД (нужен для rate limit per email и отправки).

### 152-ФЗ

- При первой `verify-otp` (создание User) фиксируется `acceptedPrivacyPolicyVersion` = `process.env.PRIVACY_POLICY_VERSION` (константа, текст политики в Phase 1.5).
- `DELETE /me` → soft-delete. Cron `user_hard_delete_30d` (Phase 1.3) делает hard-delete через 30 дней. Cascade удаляет memberships / refresh-tokens / otp-codes.
- Если удалённый user — единственный owner семьи, family также soft-delete через 30 дней.
- В БД хранится только РФ-локация (уже в scope Phase 0.3).

## Testing (TDD обязательно)

### Unit (Jest + ts-jest)

- `OtpService.generate`, `OtpService.verify` (с моками Prisma).
- `RefreshTokenService.rotate`, `.detectReplay`.
- `JwtService.signAccessToken`, `.verifyAccessToken` (clock-skew).
- `AuthService.verifyOtp` — логика auto-create User + Family + Membership при первом входе.

### Integration (Jest + supertest + testcontainers)

- Каждый endpoint — отдельный describe. Реальный Postgres через `@testcontainers/postgresql`, MailHog fake через собственный `FakeOtpDeliveryProvider` (перехватывает `send()` в массив в памяти).
- Flow end-to-end: `request-otp` → читаем код из fake delivery → `verify-otp` → проверяем JWT + refresh → `GET /me` → `refresh` → `logout` → retry `GET /me` возвращает 401.
- Replay detection: `verify-otp` → `refresh` → повторно отправляем старый refresh → 401 + все refresh revoked.
- Rate-limit: цикл 4 × `request-otp` на один email → 4-й возвращает 429.
- `PATCH /family/:id` от не-owner → 403.
- `DELETE /me` → `GET /me` с тем же access-token после этого → 401; все refresh revoked.

### Contract

- `packages/shared-types/openapi/auth.yaml` валидируется через `@apidevtools/swagger-parser`.
- Реальные ответы integration-тестов проверяются jest-matcher'ом против OpenAPI schema.

### TDD-цикл

Для каждой use-case: integration test (RED, endpoint ещё не существует) → unit-тесты по мере реализации (RED→GREEN) → integration зеленеет → refactor. Никаких «добавлю тесты потом».

## Открытые вопросы (решаются в writing-plans)

1. Library для argon2id: `argon2` (native bindings) или `@node-rs/argon2` (rust, без postinstall build). Рекомендую `@node-rs/argon2` — быстрее, без gyp.
2. Library для JWT: `jsonwebtoken` (класс-компонент) или `jose` (современный, нативные Web Crypto API). Рекомендую `jose`.
3. Email-template engine: plain string template, `handlebars`, или `react-email`. Рекомендую plain template на 1.1 (одно письмо), react-email — если понадобится >3 шаблонов.
4. Структура `packages/shared-types/openapi/` — один файл `openapi.yaml` или split по доменам (`auth.yaml`, `family.yaml`)? Рекомендую split с `$ref` — чище и codegen умеет.
