# GMD Phase 0.4 — Monitoring (GlitchTip + Uptime Kuma)

**Дата:** 2026-04-19
**Статус:** Design approved, готов к writing-plans
**Scope:** Error tracking + uptime monitoring + алерты. Observability-стек (Grafana/Loki/Prometheus) откладывается в Phase 0.5.

## Цель

Поднять на prod-сервере `192.168.1.23` два сервиса — **GlitchTip** (error tracking, Sentry-совместимый) и **Uptime Kuma** (uptime-мониторинг + алерты), — интегрировать их с backend (NestJS) и web (Next.js), настроить Telegram-бот для алертов, документировать доступ через SSH-туннель.

После Phase 0.4:

- Любая 5xx или необработанное исключение в backend/web попадает в GlitchTip.
- Падение любого критического endpoint (backend, web, Caddy, БД, Redis, TLS-сертификат, бэкапы) даёт Telegram-уведомление админу в течение 2-3 минут.
- Админ смотрит оба UI через SSH-туннель с dev-машины. Наружу ничего нового не светится.

## Контекст

Текущая инфраструктура (после Phase 1.3):

- Prod: `192.168.1.23`, внешний IP `95.104.240.99` (проброс портов `80/443 → 192.168.1.23`).
- Домен: `gmd.link28rus.ru`, TLS терминируется внешним `nginx/1.24.0 (Ubuntu)` на `95.104.240.99:443`, наш Caddy на `192.168.1.23:80` — HTTP-only.
- Request chain: `Client → nginx (TLS) → Caddy → backend/web`.
- Мониторинга нет. Ошибки ловим только через `docker logs`. Падения замечаем постфактум.
- В `docker-compose.prod.yml` уже заведены env-переменные `SENTRY_DSN_BACKEND`, `SENTRY_DSN_WEB` (пустые).
- В `Caddyfile` закомментированы блоки для `{$GLITCHTIP_DOMAIN}` / `{$KUMA_DOMAIN}` — **не используем**, переводим оба сервиса на SSH-туннель.

## Архитектурные решения

### Решение 1. Публичный доступ → SSH-туннель

Админ-панели GlitchTip и Uptime Kuma **не публикуются** через внешний nginx. Доступ только через `ssh -L` с dev-машины.

**Альтернативы рассмотрены:**

- **Subdomain через внешний nginx** (`glitchtip.gmd.link28rus.ru`, `kuma.gmd.link28rus.ru`) — требует правок на внешнем nginx + A-записей в DNS `link28rus.ru`. Отклонено: лишняя атак-поверхность для админ-панелей, дополнительная зависимость от владельца внешнего nginx, basic-auth слабая защита.
- **Caddy + Let's Encrypt напрямую** — требует перестройки TLS-стека, который сейчас работает. Отклонено: слом работающего рубежа ради двух внутренних сервисов.

**Решение:** SSH-туннель. `ssh -L 3010:127.0.0.1:8000 -L 3011:127.0.0.1:3001 gmd-prod` — открывает локальные порты `3010` (GlitchTip) и `3011` (Uptime Kuma). Контейнеры биндятся на `127.0.0.1` внутри VM (чтобы UFW не пришлось трогать).

**Исключение на будущее:** когда появится Phase 3 (mobile-child Flutter), нам понадобится публичный endpoint для приёма DSN-событий с устройств. Добавим один узкий subdomain, разрешающий только пути `POST /api/*/store/` и `POST /api/*/envelope/`. Остальной GlitchTip UI остаётся в туннеле. Это **не входит** в scope Phase 0.4.

### Решение 2. Отдельные PostgreSQL и Redis для GlitchTip

GlitchTip требует Postgres и Redis. Используем **отдельные** инстансы, не шарим с основной БД проекта.

**Причины:**

1. Upgrade-цикл GlitchTip может требовать своей версии PG; апгрейд не должен блокировать миграции основной БД.
2. GlitchTip генерирует много мелких insert'ов (события) — отдельный WAL и bloat не смешивается с основным.
3. Чистое разделение бэкапов и retention (основная БД: 30 дней WAL, GlitchTip: 7 дней дампов).
4. Компрометация/баг GlitchTip не даёт прямой доступ к ПДн в основной БД.

Цена: ~300 MB RAM + ~2 GB диска. У VM swap 4G + hdd с запасом — приемлемо.

### Решение 3. Error tracking — Sentry SDK v9 (latest stable major)

**Обновлено 2026-04-20** (изначально планировалось v7): при реализации Task 7 обнаружилось, что `@sentry/nestjs` как отдельный пакет появился только с **v8+** — в v7 его не было. На v7 пришлось бы руками писать NestJS exception-filter, что увеличивает boilerplate и риски.

Решение: **фиксируем версии `@sentry/*` на `^9.x`** во всех приложениях (`@sentry/node`, `@sentry/nestjs`, `@sentry/nextjs`). Причины:

- **GlitchTip v4 совместим** с Sentry SDK v9 через стандартный envelope format (`/api/*/envelope/` endpoint стабилен с v3+).
- **v9 — последний зрелый LTS**; v10 только что вышла и ещё минорно эволюционирует, v8 имела нестабильный wire-format (изначальная причина закрепиться на v7).
- `@sentry/nestjs@^9` предоставляет `SentryModule.forRoot()` и автоматический `APP_FILTER` — убирает 30-50 строк boilerplate.
- `beforeSend(event, hint)` API и `Event` тип стабильны с v6+ — код `scrub-pii.ts` и `shouldSendEvent` пишется одинаково для v7/v8/v9.

Откат к v7 возможен одним rollback-коммитом + ручным exception-filter'ом, если v9 покажет несовместимость на prod (риск оценён как минимальный).

### Решение 4. PII scrubbing — обязательно, фильтр 4xx — да

152-ФЗ требует, чтобы ПДн не утекали в инфраструктурный сервис. Даже GlitchTip на нашем же сервере формально является отдельной системой обработки.

**`beforeSend` вычищает:**

- `email`, `phone`, `password`, `otp`
- `token`, `refreshToken`, `accessToken`, `deviceToken`
- `dateOfBirth`, `lat`, `lng`
- `childDeviceId`, `childId` (сами UUID не ПДн, но ссылаются на конкретного ребёнка — осторожнее)

**Фильтр `beforeSend`** отбрасывает 4xx-исключения (`UnauthorizedException`, `BadRequestException`, `ForbiddenException`, `NotFoundException`, `ThrottlerException`) — это нормальный user-флоу, не ошибки приложения. Пропускаем только 5xx и необработанные throw.

### Backend integration (NestJS)

**Пакеты:**

```
"@sentry/node": "^7.120.0",
"@sentry/nestjs": "^7.120.0"
```

**Инициализация** — `apps/backend/src/main.ts`, **до** `NestFactory.create()`:

```ts
import * as Sentry from '@sentry/node';

if (process.env.SENTRY_DSN) {
  Sentry.init({
    dsn: process.env.SENTRY_DSN,
    environment: process.env.NODE_ENV,
    release: process.env.APP_VERSION, // build-arg, значение = git describe --tags (передаём из infra/deploy/deploy.sh в compose build)
    sampleRate: 1.0,
    tracesSampleRate: 0, // не шлём transaction events, GlitchTip их не показывает
    beforeSend: scrubPii, // см. ниже
  });
}
```

**`scrubPii(event)`** — утилита в `apps/backend/src/common/monitoring/scrub-pii.ts`:

- Рекурсивно обходит `event.request.data`, `event.request.headers`, `event.extra`, `event.contexts`, `event.breadcrumbs[*].data`.
- Заменяет значения ключей из блоклиста на `'[Scrubbed]'`.
- Блоклист (константа): `['email','phone','password','otp','token','refreshToken','accessToken','deviceToken','dateOfBirth','lat','lng','latitude','longitude']`.
- Дополнительно: если `event.exception.values[*].value` содержит email-regex — заменяем на `[Scrubbed email]`.

**`beforeSend` также:**

- Возвращает `null` если `event.exception.values[0].type` входит в `['UnauthorizedException','BadRequestException','ForbiddenException','NotFoundException','ThrottlerException','ValidationError']`. Это 4xx, не шлём.

**Модуль `SentryModule.forRoot()`** в `AppModule` — даёт автоматический interceptor для необработанных исключений.

**Тесты** (`scrub-pii.spec.ts`):

- Scrubbing каждого поля из блоклиста.
- 4xx не шлётся (mock `Sentry.captureException`).
- 5xx шлётся.
- Nested объекты.
- Массивы (`event.breadcrumbs`).

### Web integration (Next.js)

**Пакет:**

```
"@sentry/nextjs": "^7.120.0"
```

**Проблема client-side DSN:** GlitchTip доступен только внутри docker-сети (`http://glitchtip-web:8000`). Браузер пользователя эту сеть не видит. Публичный endpoint для приёма событий мы **сознательно не поднимаем** (Решение 1, SSH-tunnel only).

**Решение: Sentry tunnel через own API route.** Sentry SDK v7 для Next.js поддерживает опцию `tunnel: '/api/sentry-tunnel'` — клиент в браузере шлёт envelope на **свой же домен**, Next.js route handler принимает и пересылает в `http://glitchtip-web:8000/...` изнутри docker-сети.

**Файлы:**

- `apps/web/sentry.client.config.ts` — `tunnel: '/api/sentry-tunnel'`, DSN = `NEXT_PUBLIC_SENTRY_DSN` (его hostname игнорируется SDK при заданном tunnel, но `project_id` из DSN обязателен).
- `apps/web/sentry.server.config.ts` — прямой DSN, **без** tunnel (server Next.js в docker-сети, достаёт `glitchtip-web:8000` напрямую).
- `apps/web/sentry.edge.config.ts` — edge runtime; у нас App Router без edge-рантайма, оставляем минимальную инициализацию для совместимости.
- `apps/web/app/api/sentry-tunnel/route.ts` — POST handler:
  - Парсит первую строку envelope (JSON header), проверяет `dsn` — должен совпадать с `NEXT_PUBLIC_SENTRY_DSN` (защита от использования нашего tunnel для левых DSN).
  - Делает `fetch` на `http://glitchtip-web:8000/api/${projectId}/envelope/` с телом и нужными заголовками.
  - Возвращает 200 даже при фейле backend'а (не блокируем пользовательский ответ, но логируем через `console.error`).
  - `force-dynamic` + runtime `nodejs` (не edge).

Во всех трёх config-файлах — тот же `scrubPii` (shared util в `apps/web/src/lib/monitoring/scrub-pii.ts`; дублирует backend-версию — две разные кодовые базы, выносить в `packages/shared-types` не имеет смысла, т.к. это runtime-логика, а не типы).

**`next.config.js`** — обёртка `withSentryConfig`:

- `silent: true` (без логов SDK во время build)
- `hideSourceMaps: true`
- `disableServerWebpackPlugin: true`, `disableClientWebpackPlugin: true` (не грузим source-maps в GlitchTip — out of scope, см. YAGNI)

**Env:**

- `NEXT_PUBLIC_SENTRY_DSN` (build-arg, запекается в client bundle — уже есть в compose `args`). Значение формата `http://<key>@glitchtip-web:8000/2` — **hostname не критичен** при заданном tunnel, но SDK требует валидный DSN; pragmatic value = `NEXT_PUBLIC_API_URL`-хост + project_id = 2.
- `SENTRY_DSN_WEB` (server-side, runtime env) = `http://<key>@glitchtip-web:8000/2` — реальный internal DSN.

**Тесты:**

- Unit: `scrub-pii.spec.ts` для web (параллельно backend-версии).
- Integration: Playwright smoke-тест — отрендерить страницу с `throw new Error('phase-0.4-smoke-test')` в server component → проверить через GlitchTip API (`GET /api/0/projects/gmd/web/events/`), что событие появилось в течение 30 секунд.
- Integration client-side: Playwright — перейти на страницу, через `page.evaluate(() => { throw new Error('client-smoke') })` кинуть ошибку в окно браузера, проверить что в GlitchTip появилось событие с `platform: 'javascript'` (через tunnel). Сам tunnel endpoint покрывается acceptance #3.

### Backup integration

**`infra/server-setup/scripts/pg-backup.sh`** — обновить:

```bash
# существующий дамп основной БД
pg_dump ... > /opt/gmd/backups/postgres/gmd-$(date +%F).sql.gz

# новый: дамп GlitchTip-БД
docker exec gmd-glitchtip-postgres pg_dump -U glitchtip glitchtip | \
  gzip > /opt/gmd/backups/glitchtip/glitchtip-$(date +%F).sql.gz

# retention 7 дней для glitchtip
find /opt/gmd/backups/glitchtip -name '*.sql.gz' -mtime +7 -delete

# heartbeat в Uptime Kuma
curl -fsS "$KUMA_BACKUP_HEARTBEAT_URL" || true
```

**`$KUMA_BACKUP_HEARTBEAT_URL`** — push-URL монитора #8, лежит в `/opt/gmd/.env.prod` (на сервере, не в git).

**Uptime Kuma volume** — снэпшот tar раз в день через отдельный скрипт `infra/server-setup/scripts/kuma-backup.sh`:

```bash
tar czf /opt/gmd/backups/uptime-kuma/kuma-$(date +%F).tar.gz -C /opt/gmd/data uptime-kuma
find /opt/gmd/backups/uptime-kuma -mtime +7 -delete
```

Оба скрипта запускаются уже существующим systemd-timer'ом `pg-backup.timer` (переименовать в `gmd-backup.timer` или добавить второй — решит writing-plans).

### SSH-config обновление

Dev-машина `~/.ssh/config`:

```
Host gmd-prod
    HostName 192.168.1.23
    User root
    IdentityFile ~/.ssh/id_ed25519_gmd
    # монитор-туннели (открываются по ssh gmd-prod-tunnels)

Host gmd-prod-tunnels
    HostName 192.168.1.23
    User root
    IdentityFile ~/.ssh/id_ed25519_gmd

    LocalForward 3011 127.0.0.1:3001
    ServerAliveInterval 60
    ExitOnForwardFailure yes
```

```
TELEGRAM_BOT_TOKEN=<bot token>
TELEGRAM_ADMIN_CHAT_ID=<chat id>
```

Секреты копируются в `save_secret` в memory-compiler (project `gmd`).

## Acceptance criteria

Фаза считается завершённой когда:

1. `ssh gmd-prod-tunnels -N` + браузер → GlitchTip и Uptime Kuma открываются, логин работает.
2. В backend вызван `throw new Error('phase-0.4-smoke-test')` — событие появляется в GlitchTip project `backend` в течение 30 секунд.
3. В Next.js вызван `throw new Error('phase-0.4-smoke-test')` в server component — событие появляется в project `web` в течение 30 секунд.
   3a. В Next.js в browser-runtime кинута ошибка (`page.evaluate(() => { throw new Error('client-smoke') })`) — envelope уходит через `/api/sentry-tunnel`, событие появляется в project `web` с `platform: javascript`.
4. **PII scrubbing верифицирован**: в сохранённом событии поля email/phone/token/lat/lng равны `[Scrubbed]`.
5. **4xx filter верифицирован**: вызов `GET /api/admin/foo` без auth даёт `401` в логе backend, но **не** даёт событие в GlitchTip.
6. Все 8 мониторов Uptime Kuma зелёные (UP).
7. Тест-алерт `critical`: `docker stop gmd-backend` → Telegram-сообщение приходит в течение 3 минут, email — в течение 5 минут. После `docker start gmd-backend` — recovery-сообщение.
8. `pg-backup.sh` выполнен вручную → дамп GlitchTip появился в `/opt/gmd/backups/glitchtip/`, heartbeat дошёл до Kuma (монитор #8 зелёный).
9. `/opt/gmd/data/uptime-kuma` бэкап появился в `/opt/gmd/backups/uptime-kuma/`.
10. `docs/monitoring.md`, `docs/deploy.md`, `docs/backup-restore.md`, `CHANGELOG.md`, `CLAUDE.md` обновлены и закоммичены.
11. Admin-пароли GlitchTip и Kuma, Telegram bot token сохранены в memory-compiler через `save_secret`.
12. `save_tracking gmd/release v0.12.0`.

## YAGNI / out of scope

- **Grafana + Loki + Prometheus** — откладывается в Phase 0.5 (после Phase 3 когда появится mobile-трафик).
- **Sentry performance monitoring (transactions / APM)** — GlitchTip не поддерживает полноценно.
- **PagerDuty / Opsgenie / on-call rotation** — один админ, Telegram+email хватает.
- **Log aggregation (docker-json → Loki/ELK)** — откладывается. Пока хватает `docker logs` через SSH.
- **Source-maps upload в GlitchTip для web** — откладывается, усложняет CI, а на MVP стек-трейсы client-side пока без source-maps читаемы.
- **Публичный endpoint DSN** — добавим в Phase 3, когда понадобится для mobile.
- **Auto-restore smoke-test для GlitchTip-бэкапа** — откладывается; данные не критичные, 7-дневный дамп достаточен.

## Риски

| Риск                                                                            | Митигация                                                                                                                                           |
| ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| GlitchTip раздует диск событиями                                                | Retention 30 дней + монитор #7 (disk-space)                                                                                                         |
| Утечка ПДн через необработанное поле                                            | `scrub-pii.spec.ts` с исчерпывающим блоклистом + code review + smoke-test через acceptance #4                                                       |
| OOM на VM при пике событий                                                      | GlitchTip celery worker ограничен по concurrency=2; в `.env.prod`: `CELERY_WORKER_CONCURRENCY=2`                                                    |
| Telegram-бот упал/заблокирован                                                  | Email-fallback на critical алерты                                                                                                                   |
| Первый запуск GlitchTip: admin registration открыт — кто-то может зарегать user | Регистрируем сразу после `docker compose up`, следующим шагом выключаем `ENABLE_USER_REGISTRATION=False`. Время окна < 5 минут + не светимся наружу |
| Потеря пароля Kuma / GlitchTip                                                  | Админ-пароль в memory-compiler `save_secret`; при утере можно сбросить через `docker exec` внутри UI-утилит обоих сервисов                          |
