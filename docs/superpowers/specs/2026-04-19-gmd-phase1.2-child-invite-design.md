# GMD Phase 1.2 — Child Invite + Device Token

**Дата:** 2026-04-19
**Фаза:** 1.2 (backend)
**Зависит от:** Phase 1.1 (Auth + Family, v0.4.0) — используется Family/Membership, JwtAuthGuard.

## Цель

Родитель может создать в своей семье ребёнка, сгенерировать одноразовый invite-код (QR) и привязать к этому ребёнку детское устройство. Устройство получает long-lived device-token, которым авторизуется в child-API. Родитель может сбросить устройство (инициировать повторную привязку) и удалить ребёнка.

## Scope

**Входит:**

- Модели `Child`, `Invite`, `ChildDevice`.
- Parent-endpoints: `POST /family/children`, `GET /family/children`, `PATCH /family/children/:id`, `DELETE /family/children/:id`, `POST /family/children/:id/invites`, `POST /family/children/:id/reset-device`.
- Child-endpoints: `POST /child/claim`, `GET /child/me`.
- `ChildAuthGuard` по header `X-Child-Token`.
- Invite-code: 8 chars Crockford Base32, TTL 10 min, одноразовый.
- Device-token: opaque 32-byte base64url, `sha256(token)` в БД, без TTL (long-lived).
- Расширение `GET /me` полем `children[]`.
- Rate limiting на `/child/claim`.
- Web-лендинг `/claim/[code]` в Next.js с инструкцией (без deep-link на MVP).
- Unit-тесты для всех сервисов + e2e на testcontainers.

**Не входит** (следующие фазы):

- Push-token регистрация (FCM / RuStore) — «notifications» фаза.
- Heartbeat endpoint `POST /child/heartbeat` — Phase 2 (locations).
- Android App Links / iOS Universal Links — mobile-фаза.
- Rotation device-token — YAGNI на MVP.
- Multi-device на ребёнка — YAGNI.
- Согласие 14+ (ФЗ-152) — Phase 1.2.5 вместе с юр. документами.
- Hard-delete cron для Child — Phase 1.3.
- UI для parent «Дети» и «Создать ребёнка» в web-кабинете — Phase 1.2-web.
- UI для сканирования QR в child-приложении — Phase 3 (mobile-child).

## Решения (через brainstorming)

| Вопрос                | Решение                                                | Почему                                                                                                             |
| --------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| Scope                 | B: MVP invite + lifecycle (reset-device, delete child) | Готовая база для Phase 2, minimal production pattern                                                               |
| Invite формат         | 8 chars Crockford Base32 (без `I L O U`)               | Человекочитаемо (можно продиктовать); 32⁸ ≈ 10¹² хватает при 10m TTL + rate-limit                                  |
| Invite хранение       | Plain в БД, не хешируется                              | Код — human-readable, защита через TTL + rate-limit. Хеш только добавил бы сложность без выгоды                    |
| Device-token          | Opaque 32-byte base64url, sha256 в БД, long-lived      | Аналогично refresh-token. Long-lived потому что устройство хранит в Android Keystore, а smena — через parent reset |
| QR URL                | `https://gmd.link28rus.ru/claim/{code}`                | Работает и как deep-link (позже), и как web-лендинг сейчас                                                         |
| Один device на child  | `ChildDevice.childId @unique`, 409 при повторном claim | Родитель контролирует смену устройства через reset-device                                                          |
| Auth header для child | `X-Child-Token`, не `Authorization: Bearer`            | Чётко отделяет parent-JWT от child-device-token для middleware/audit                                               |
| Согласие 14+          | Отложено в Phase 1.2.5                                 | Вместе с политикой конфиденциальности и юр. документами                                                            |

## Архитектура

### Data model (Prisma)

```prisma
model Child {
  id          String    @id @default(cuid())
  familyId    String
  name        String
  dateOfBirth DateTime?
  avatarKey   String?
  createdAt   DateTime  @default(now())
  updatedAt   DateTime  @updatedAt
  deletedAt   DateTime?

  family  Family       @relation(fields: [familyId], references: [id], onDelete: Cascade)
  device  ChildDevice?
  invites Invite[]

  @@index([familyId])
  @@index([familyId, deletedAt])
  @@map("children")
}

model Invite {
  id         String    @id @default(cuid())
  familyId   String
  childId    String
  code       String    @unique
  expiresAt  DateTime
  consumedAt DateTime?
  createdBy  String
  createdAt  DateTime  @default(now())

  family Family @relation(fields: [familyId], references: [id], onDelete: Cascade)
  child  Child  @relation(fields: [childId], references: [id], onDelete: Cascade)

  @@index([familyId, consumedAt])
  @@index([childId, consumedAt])
  @@map("invites")
}

model ChildDevice {
  id         String    @id @default(cuid())
  childId    String    @unique
  tokenHash  String    @unique
  deviceName String?
  osVersion  String?
  appVersion String?
  lastSeenAt DateTime?
  revokedAt  DateTime?
  createdAt  DateTime  @default(now())

  child Child @relation(fields: [childId], references: [id], onDelete: Cascade)

  @@map("child_devices")
}
```

Relations на существующих моделях (Family добавляет `children Child[]`, Invite — в `Family`).

**Soft-delete:** `Child.deletedAt`. Cascade на `ChildDevice` и `Invite` при `onDelete: Cascade`, но при soft-delete `Child` (без hard DELETE) каскада не произойдёт — revoke `ChildDevice` делаем явно в `ChildrenService.softDelete`.

**Миграция:** `prisma migrate dev --name child_invite`. В prod применяется через `bash infra/deploy/deploy.sh`.

### Ключевые сервисы

```typescript
// children.service.ts
@Injectable()
class ChildrenService {
  constructor(prisma: PrismaService) {}

  createChild(familyId: string, input: {name: string, dateOfBirth?: Date}): Promise<Child>
  listChildren(familyId: string): Promise<ChildWithDevice[]>       // + device eager-loaded
  getChildInFamily(familyId: string, childId: string): Promise<Child | null>
  updateChild(familyId: string, childId: string, patch: {...}): Promise<Child>
  softDelete(familyId: string, childId: string): Promise<void>     // revoke device + soft-delete child
}

// invites.service.ts
class InvitesService {
  constructor(prisma, childrenService, codeGenerator) {}

  createInvite(familyId: string, childId: string, createdBy: string): Promise<InviteWithCode>
    // throws 404 если child не в семье
    // throws 409 если у child есть non-revoked device
  resetDevice(familyId: string, childId: string): Promise<void>
    // throws 404 если нет active device
}

// child-device.service.ts
class ChildDeviceService {
  constructor(prisma) {}

  claim(code: string, meta: ClaimMeta): Promise<ClaimResult>
    // transaction:
    //   1. SELECT invite WHERE code = $1 AND consumedAt IS NULL AND expiresAt > now()
    //      (FOR UPDATE, чтобы race condition не было)
    //   2. если нет → throw 400 invite_invalid
    //   3. SELECT child_devices WHERE childId = invite.childId AND revokedAt IS NULL
    //      если есть → throw 409 child_has_device
    //   4. INSERT child_devices + SET invite.consumedAt = now()
    //   5. RETURN { deviceToken, child }
  verifyToken(token: string): Promise<ChildAuthContext | null>
    // SELECT child_devices WHERE tokenHash = sha256(token) AND revokedAt IS NULL
    // + JOIN child (не-deleted)
  touchLastSeen(deviceId: string): void  // не-блокирующее обновление
}

// lib/code-generator.ts
const ALPHABET = '0123456789ABCDEFGHJKMNPQRSTVWXYZ';  // 32 символа, Crockford
function generateInviteCode(): string {   // 8 random chars
  let s = '';
  for (let i = 0; i < 8; i++) s += ALPHABET[crypto.randomInt(0, 32)];
  return s;
}
```

### Child auth guard

```typescript
@Injectable()
class ChildAuthGuard implements CanActivate {
  constructor(private readonly svc: ChildDeviceService) {}

  async canActivate(ctx: ExecutionContext): Promise<boolean> {
    const req = ctx.switchToHttp().getRequest();
    const token = req.headers['x-child-token'];
    if (!token || typeof token !== 'string') {
      throw new UnauthorizedException({ code: 'unauthorized', message: 'Missing X-Child-Token' });
    }
    const device = await this.svc.verifyToken(token);
    if (!device) {
      throw new UnauthorizedException({ code: 'unauthorized', message: 'Invalid token' });
    }
    req.childDevice = device; // { childId, deviceId, familyId, childName }
    // fire-and-forget update lastSeenAt
    void this.svc.touchLastSeen(device.deviceId);
    return true;
  }
}
```

## Security

### Invite-code

- 8 Crockford Base32 chars (исключены `I L O U`): `0123456789ABCDEFGHJKMNPQRSTVWXYZ`.
- `crypto.randomInt(0, 32)` × 8.
- TTL 10 min, одноразовый.
- Кейсо-нечувствительный verify (normalize to upper).
- Brute-force: rate-limit на `/child/claim` + counter `wrong_attempts` в Redis per-code с TTL 10 min (после 5 wrong — код считается invalid).
- **Не хешируется** в БД — это не секрет длительного хранения, а расходный токен. Защита через краткое TTL и rate-limit.

### Device-token

- 32-byte random, base64url encoded (43 chars).
- Plain только в ответе `/child/claim` (и в памяти устройства).
- В БД `tokenHash = sha256(token)` с unique index.
- Long-lived: нет TTL. Revoke через parent (`reset-device`, `DELETE /child`).
- `lastSeenAt` обновляется на каждом authed запросе (без блокировки request).

### Race condition в claim

- Проблема: два устройства одновременно сканят один код. Без транзакции оба могут получить OK.
- Решение: Prisma `$transaction` с изоляцией `Serializable`, либо pessimistic lock через `SELECT ... FOR UPDATE` (raw SQL).
- Выбираем pessimistic lock: `tx.$queryRawUnsafe` для `SELECT id FROM invites WHERE code = $1 ... FOR UPDATE` в начале транзакции. Второй claim попадёт в row-lock и увидит уже consumed invite после коммита первого.

### Reset-device

- Просто `revokedAt = now()` на active device. Row остаётся для audit.
- Старый token криптографически валиден, но guard по `revokedAt IS NULL` отказывает.

### Enumeration defense

- `POST /child/claim` для любого невалидного кода возвращает одинаковый `400 invite_invalid` (не различает «нет в БД», «expired», «consumed»). Timing — одинаковый (min 200ms через `setTimeout`).

### 152-ФЗ

- `Child.name`, `Child.dateOfBirth` — ПДн. Soft-delete через `deletedAt`, hard-delete через 30 дней (Phase 1.3).
- `ChildDevice` не ПДн (deviceName — технический идентификатор), но удаляется каскадно.

## Testing (TDD)

### Unit

- `code-generator.spec.ts`:
  - Возвращает 8 chars из Crockford алфавита.
  - Тест 1000 кодов — все валидны, распределение равномерное.
  - Никогда не возвращает `I`, `L`, `O`, `U`.

- `invites.service.spec.ts`:
  - `createInvite` успешно если у child нет device.
  - 409 если child.device.revokedAt = null.
  - Успех если device.revokedAt != null.
  - `resetDevice` revoke'ит active device.
  - `resetDevice` 404 если нет active.

- `child-device.service.spec.ts`:
  - `claim` валидного кода → insert + invite.consumedAt.
  - `claim` expired → 400 invite_invalid.
  - `claim` consumed → 400 invite_invalid.
  - `claim` уже есть device → 409 child_has_device.
  - `claim` несуществующий код → 400 invite_invalid.
  - `verifyToken` revoked → null.
  - `verifyToken` deleted child → null.
  - `verifyToken` valid → context.

- `children.service.spec.ts`:
  - CRUD.
  - `softDelete` revoke'ит device + все invites mark как consumed.

- `child-auth.guard.spec.ts`:
  - Нет header → 401.
  - Invalid token → 401.
  - Valid token → true + req.childDevice.

### Integration (testcontainers)

- `children.e2e-spec.ts`:
  - Parent создаёт child → GET list → виден без device.
  - PATCH name → отражается в list.
  - Parent не видит children чужой семьи (404 на PATCH/DELETE чужого).
  - DELETE child → list пуст.
  - DELETE child с active device → device тоже revoked.

- `child-device.e2e-spec.ts`:
  - Full flow: parent создаёт child → invite → claim → child GET /me.
  - После claim повторно тот же код → 400 invite_consumed.
  - После parent reset-device → старый token → 401, новый invite → новый claim работает.
  - Invalid код → 400 (код не содержит детали какая именно проблема).
  - Parent DELETE child → child token → 401 (deleted).
  - Rate limit: 11-й `/child/claim` → 429.

## Открытые вопросы (для writing-plans)

1. Модификация `Family` model — добавить relation `children Child[]` или нет? Рекомендую да (удобно в query, иначе всегда фильтр по `familyId`).
2. Как именно делать `SELECT FOR UPDATE` в Prisma? Вариант: `tx.$queryRawUnsafe<Array<{id: string}>>('SELECT id FROM invites WHERE code = $1 AND consumed_at IS NULL AND expires_at > NOW() FOR UPDATE', normalizedCode)`. Альтернатива — `Isolation.Serializable` + retry. Рекомендую raw FOR UPDATE (проще).
3. Enumeration timing — на `/child/claim` делать min 200ms ответ или нет? Рекомендую да (как на `/auth/request-otp`).
4. Нормализация кода — принимать lowercase и приводить к upper? Рекомендую да (удобство ввода).
