# Состояние разрешений ребёнка (#63)

Нативный `PermissionStateReportWorker` собирает состояние без Flutter-движка.
WorkManager запускает проверку примерно раз в 6 часов при наличии сети.
Дополнительные отчёты запрашиваются при старте процесса, возврате в приложение,
перезагрузке, обновлении APK, изменении Device Admin и запросе родителя.
Проверка boot/update стоит до проверки разрешения геолокации.

## API

- `POST /child/permission-state`, `X-Child-Token`: `{sequence, permissions}`.
  `sequence` — положительное безопасное целое; `permissions` — полный набор
  ключей из `PermissionsSchema`, значения `true`, `false`, `null`.
- `GET /family/children/:childId/permission-state`, JWT семьи: состояние,
  серверное время приёма отчёта и читаемый список отключённых разрешений.
- `POST /family/children/:childId/refresh-permission-state`, JWT семьи:
  `{requested}` означает принятие запроса каналом доставки, а не получение отчёта.
  Используется существующая гибридная доставка команд. Если канал недоступен,
  следующая периодическая проверка остаётся запасным путём.
  Для запроса отчёта используются WebSocket и FCM: детский RuStore data-handler
  пока не исполняет эту команду, поэтому приём RuStore не выдаётся за успешный запрос.
- `GET /family/children` дополнительно отдаёт `device.permissionState`.
  Хеш привязки, sequence и очередь доставки в клиентский ответ не попадают.

## Переходы и доставка

Первый отчёт создаёт исходное состояние без массовой рассылки. Уведомление
`PERMISSION_DEGRADED` создаётся при переходе известного `true` в `false`.
Неизменившийся отчёт продлевает свежесть; повторный или старый sequence игнорируется.
`lastKnown` сохраняет последнее известное значение через неудачную проверку (`null`),
но интерфейс показывает текущий неполный отчёт как неизвестное состояние.

Данные старше 18 часов показываются как устаревшие. Accessibility и Usage Stats
имеют `null`: соответствующие функции сейчас отключены. Отсутствующий Device Admin
не считается проблемой, когда родитель выключил защиту от удаления.

Состояние и события создаются в одной транзакции с блокировкой строки устройства.
Хеш действующего токена отделяет старый телефон при перепривязке. Отправки хранятся
по каждому устройству родителя; перед отправкой перепроверяются семья, активность
устройства/пользователя и актуальность проблемы. Lease ограничивает параллельную
обработку. Ошибка провайдера повторяется через 5 минут; сервер проверяет очередь
раз в минуту. Восстановление отменяет ожидающие события, включая ошибку отправки
в полёте. Устаревшие события не отправляются спустя сутки; записи удаляются через 7 дней.

Доставка имеет семантику **как минимум одна попытка с повтором**: падение после
приёма push провайдером и до сохранения результата может дать повтор.
Успех FCM/RuStore не доказывает отображение на телефоне. FCM обрабатывается
нативным сервисом родителя; RuStore получает видимый `notification` и открывает
экран ребёнка после восстановления сессии.
События не объединяются через FCM collapse key. Android-уведомление имеет ID
по `alertId`: повторы события обновляют одну запись, разные отзывы сохраняются
даже при обратном порядке доставки. Текст включает все известные текущие проблемы.

Холодный тап RuStore читается через `getInitialMessage()` SDK 7.2.0. Этот SDK
хранит входящие сообщения в памяти процесса: после его убийства до нажатия
уведомления исходное сообщение может отсутствовать, тогда открывается главный экран.

## Проверка перед выпуском

Автотесты: `permission-state.spec.ts`, `permission-state.e2e-spec.ts`,
`fcm-permission.spec.ts`, web `permission-state-card.test.tsx`,
Flutter `permission_state_test.dart`, `push_permission_startup_test.dart`,
Kotlin `PermissionSnapshotTest` и `PermissionNotificationTextTest`.

Для проверки на устройстве нужны обновлённые APK ребёнка и родителя и миграция
`20261117010000_child_permission_state`. Сначала получить полный исходный отчёт,
затем отключить микрофон или другое используемое разрешение, проверить push,
переход по нажатию и карточку. Повторить с восстановлением, без открытия детского
UI, после перезагрузки/обновления и с недоступной сетью.

Force-stop, ограничения производителя и отсутствие сети могут задерживать
WorkManager. Мгновенное обнаружение и реальная доставка на физическом телефоне
автотестами сервера не подтверждаются.
